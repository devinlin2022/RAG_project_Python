# rag-agent

Online RAG assistant based on Gradio, SiliconFlow / Ollama

一个按页抽取、按结构切分、可逐步扩展的文档问答服务。当前为 **V2**：在 V1 的「PDF → 按页抽取 → 页级标记 → 页级问答」闭环之上，补齐了**文档读得对不对**和**切得对不对**两件事——扫描页/表格页/图形页的分通道增强识别，以及四种切分策略与自动推荐。

页面与接口由同一进程提供，共享同一份文档状态。

> 代码约定：代码中的注释与 docstring 使用英文；界面文案与错误提示使用中文。

## 环境配置（硅基流动 DeepSeek）

### 1. 获取 API Key

1. 注册并登录 [硅基流动控制台](https://cloud.siliconflow.cn)
2. 打开「API 密钥」页面（<https://cloud.siliconflow.cn/account/ak），新建密钥>
3. 复制以 `sk-` 开头的完整字符串（只显示一次）

### 2. 创建配置文件

```bash
cp .env.example .env          # Windows: copy .env.example .env
```

`.env` 位于项目根目录，已被 `.gitignore` 忽略，不会提交到仓库。

### 3. 填写三个核心变量

| 变量             | 硅基流动的取值                         | 说明                       |
| -------------- | ------------------------------- | ------------------------ |
| `LLM_BASE_URL` | `https://api.siliconflow.cn/v1` | **必须包含末尾的 `/v1`**，否则 404 |
| `LLM_API_KEY`  | `sk-xxxxxxxxxxxxxxxx`           | 控制台复制的完整密钥，不要带空格或引号      |
| `LLM_MODEL`    | `deepseek-ai/DeepSeek-V3`       | 模型广场中的**完整模型 ID**，不是显示名称 |

填写后的 `.env` 示例：

```dotenv
LLM_BASE_URL=https://api.siliconflow.cn/v1
LLM_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxxxx
LLM_MODEL=deepseek-ai/DeepSeek-V3

TEMPERATURE=0.2
MAX_TOKENS=1024
LLM_TIMEOUT=90
```

`LLM_BASE_URL` 与 `LLM_MODEL` 都在 `.env` 中配置，代码里没有硬编码，换模型只需改这一行。

### 4. DeepSeek 模型选择

| `LLM_MODEL` 候选            | 适用场景       | 说明                     |
| ------------------------- | ---------- | ---------------------- |
| `deepseek-ai/DeepSeek-V3` | 通用文档问答（默认） | 速度快、成本低，适合抽取型问答        |
| `deepseek-ai/DeepSeek-R1` | 需要显式推理链    | 会额外返回推理内容，首 token 延迟更高 |
| 其他 `deepseek-ai/*`        | 平台上线新版本后   | 按模型广场实际 ID 填写          |

模型 ID 随平台更新而变动，**以控制台模型广场为准**。本项目不预设枚举，运行时也不需要改动代码，只改 `.env` 的 `LLM_MODEL`。

### 4.1 国内站与国际站的模型目录不同

硅基流动有两个站，**Key 不通用，模型目录也不同**：

| 站点 | Base URL | 本项目默认模型是否可用 |
| --- | --- | --- |
| 国内站 | `https://api.siliconflow.cn/v1` | `PaddlePaddle/PaddleOCR-VL-1.5`、`BAAI/bge-m3` 均在售 |
| 国际站 | `https://api.siliconflow.com/v1` | 上述两个**没有**，需换成 Qwen 系列 |

用错站点的典型症状是 `{"code":30014,"message":"Token is invalid."}`——Key 格式完全正常（`sk-` + 48 位），只是不属于这个站。

国际站的可用替代：

| 用途 | 国内站 | 国际站 |
| --- | --- | --- |
| OCR / 图注 | `Qwen/Qwen3-VL-32B-Instruct`、`PaddlePaddle/PaddleOCR-VL-1.5`、`deepseek-ai/DeepSeek-OCR` | `Qwen/Qwen3-VL-32B-Instruct`、`Qwen/Qwen3-VL-8B-Instruct` |
| 向量 | `BAAI/bge-m3` | `Qwen/Qwen3-Embedding-8B` / `-4B` / `-0.6B` |
| 重排（V3） | `BAAI/bge-reranker-v2-m3` | `Qwen/Qwen3-Reranker-8B` |

判断方法：`curl $BASE_URL/models -H "Authorization: Bearer $KEY"`，返回 200 说明站点对了。

### 5. 验证配置

```bash
python check_llm.py          # 问答 + 向量
python check_llm.py --ocr    # 再加一次视觉调用（会计费）
```

一条命令把四类模型的**存在性**和三条通道的**连通性**都验一遍，不用等到页面上报错才发现配错站点或模型 ID 下架：

```
== 当前配置 ==
LLM_BASE_URL : https://api.siliconflow.cn/v1
LLM_MODEL    : deepseek-ai/DeepSeek-V3  (问答)
OCR_MODEL    : Qwen/Qwen3-VL-32B-Instruct  (OCR, 已启用)
VISION_MODEL : Qwen/Qwen3-VL-32B-Instruct  (图注)
EMBED_MODEL  : BAAI/bge-m3  (向量)
LLM_API_KEY  : sk-wyy…vbih

== 模型可用性 ==
平台可用模型 99 个
  OK   deepseek-ai/DeepSeek-V3                (问答)
  OK   Qwen/Qwen3-VL-32B-Instruct             (OCR/图注)
  OK   BAAI/bge-m3                            (向量)

== 连通性 ==
  OK   chat      1.3s  返回 'pong'
  OK   embed     0.3s  1024 维
  SKIP ocr       加 --ocr 可实测一次（会产生一次调用）

全部通过，可以启动：python run.py
```

带 `MISS` 的行表示该模型 ID 在当前站点不存在（常见于 `.cn` 与 `.com` 混用、或模型已下架），`402` 表示余额不足，`401` 表示 Key 不属于这个站点。

退出码：`0` 全部通过，`1` 未配置，`2` 有通道不可用，`3` 模型 ID 缺失。

### 6. 常见错误对照

| 现象                    | 原因                                 | 处理                                         |
| --------------------- | ---------------------------------- | ------------------------------------------ |
| `API Key 无效（401）`     | 密钥不完整，或复制时带入空格                     | 重新复制，确保 `sk-` 开头且无换行                       |
| `接口或模型不存在（404）`       | `LLM_BASE_URL` 缺 `/v1`，或模型 ID 拼写错误 | 核对 base_url；用 `check_llm.py` 列出 ID         |
| `连接超时` / `ProxyError` | 代理或 VPN 拦截                         | 关闭代理，或将 `api.siliconflow.cn` 加入 `NO_PROXY` |
| `HTTP 400`            | 模型不支持请求中的某个字段                      | 本项目只发送标准字段；若仍报错请贴出响应体                      |
| 页面提示「未配置 LLM_API_KEY」 | `.env` 未创建或变量名为空                   | 确认文件在项目根目录、变量拼写正确                          |

修改 `.env` 后需要重启服务才会生效。

## 公网访问（ngrok，可选）

默认只监听 `127.0.0.1`，本机访问即可。需要临时分享给他人时，用 ngrok 开一个隧道：

1. 在 [ngrok dashboard](https://dashboard.ngrok.com/get-started/your-authtoken) 复制 authtoken
2. 在 `.env` 中填写：

```dotenv
NGROK_ENABLED=true
NGROK_AUTHTOKEN=你的_tunnel_authtoken
```

3. 正常启动 `python run.py`，控制台会多打印一行：

```
公网访问链接 (Share URL): https://xxxx-xx-xx-xx-xx.ngrok-free.app
```

设计取舍：

- **token 只从 `.env` 读取，代码里不出现**。写死在 `main.py` 里的 token 一旦提交就会泄漏，而且换环境要改代码。
- **隧道失败不影响本地使用**。免费额度用尽、网络不可达、未装 `pyngrok` 时只打印一行警告，服务照常在 `127.0.0.1:7860` 起来。
- **公网暴露意味着任何人都能用你的 API Key 花钱**。本版无鉴权，分享链接请只发给可信对象，用完把 `NGROK_ENABLED` 改回 `false`。

## 增强识别：OCR / 表格 / 图形

### 为什么需要三条通道

V1 只能拿到 PDF 的文本层。三类页面在这里会丢失信息，且丢失方式不同：

| 页面类型 | V1 的结果          | 真正的问题                       | 对策                     |
| ---- | --------------- | --------------------------- | ---------------------- |
| 扫描页  | 文本为空，只能被标记为可疑   | 没有文本层，任何解析器都读不出字            | 渲染成图 → OCR           |
| 表格页  | 单元格被压成一行，表头丢失   | 结构信息在二维网格里，不在字符流里           | pdfplumber 取网格 → Markdown |
| 图形页  | 完全没有文字，或只剩零散标签  | 信息在**箭头关系**里，而不在标签里         | 视觉模型写图注，要求输出 `A -> B` |

第三条最容易被误解。**OCR 对流程图基本无用**：它只能把方框里的「提交」「复核」「归档」抄下来，抄不出「复核不通过则退回提交」。所以图形通道用的不是 OCR 提示词，而是图注提示词，明确要求列出节点、逐条写出箭头关系与分支条件。这一步不做，流程图在检索里等于不存在。

### 通道决策

每页在解析后会被路由到若干通道，决策完全基于已抽取的文本和 PDF 结构，不调用模型：

- **扫描页**：`chars < SCAN_PAGE_CHAR_THRESHOLD` → `ocr`
- **表格页**：`find_tables() > 0` 或列结构行占比 `>= TABLE_COLUMN_RATIO` → `table`
- **图形页**：嵌入图片覆盖面积 `>= 5%`，或矢量图元 `>= 60` 且正文 `< 1500` 字 → `figure`

扫描页还有一个特例：整页扫描件本身就是一张覆盖 100% 的图，覆盖率无法区分「扫描的文字页」和「扫描的图纸」。因此先跑 OCR，**若 OCR 在满覆盖页上几乎没读出字（< 120 字），再追加图注通道**——用 OCR 的结果反过来判断这页到底是文字还是图。

### 模型选择

三条通道都可以用同一个硅基流动 Key，不必再申请其他平台：

| 用途       | `OCR_MODEL` / `VISION_MODEL`    | 实测表现                                  |
| -------- | ------------------------------- | ------------------------------------- |
| OCR      | `Qwen/Qwen3-VL-32B-Instruct`    | 按提示词输出 Markdown 表格，行列对应关系可靠           |
| OCR（备选）  | `PaddlePaddle/PaddleOCR-VL-1.5` | 免费，但实测把表格输出成逐行纯文本，单页约 78 秒            |
| 图注       | `Qwen/Qwen3-VL-32B-Instruct`    | 图表理解强，能读出箭头关系                         |

PaddleOCR-VL 是专用 OCR 模型，转录纯文字扫描件没问题；但它不遵循「输出 Markdown 表格」的指令，遇到表格页会丢掉行列对应关系。因此默认用 Qwen3-VL，PaddleOCR-VL 留在「页面无表格且要压成本」的场合。

视觉调用是整条链路里唯一按页计费、且单页可能耗时十几秒的环节，所以要限速：`OCR_MIN_INTERVAL` 控制两次调用之间的最小间隔（默认 1.5 秒），遇 429 会按指数退避重试 `HTTP_RETRIES` 次。

`OCR_BASE_URL` / `OCR_API_KEY` 留空时会自动复用 `LLM_BASE_URL` / `LLM_API_KEY`。若要换成阿里百炼等其他平台，只改这两个变量即可，代码无需改动。

### 启用与成本

```dotenv
OCR_ENABLED=true
OCR_MAX_PAGES=20
ENHANCE_MAX_SECONDS=120
```

- **默认关闭**。视觉调用按页计费且每页 1–5 秒，不应在每次上传时自动触发。
- 界面上的「运行增强识别」由你手动点击；旁边的「只看路由计划」只做决策、不调用任何模型，可以先看清楚哪些页会花钱。
- 双预算：`OCR_MAX_PAGES` 限制页数，`ENHANCE_MAX_SECONDS` 限制总时长。超出的页不会被静默丢弃，而是在结果表里标为「跳过」并写明原因。
- 表格通道**离线、免费、毫秒级**，不需要 `OCR_ENABLED`，随时可用。

### 表格的两种情况

`pdfplumber.find_tables()` 只认框线。合同里大量表格是**没有框线的**——Word 导出时列只用空格对齐。这类页会被 `TABLE_COLUMN_RATIO` 正确标记为表格页，但框线检测返回 0 个表格。

因此表格通道有两级：

1. 有框线 → `find_tables()` 取网格
2. 无框线 → 从已抽取的文本里解析表格块：连续的 `A | B | C` 行，或连续多行「两段以上空格分隔、列数一致」的行

第 2 级列数不一致时（例如表头 4 列、数据 5 列）按最大列数补齐，并把首行识别为表头——首行比表体短一行，本身就是「表头缺尾列」的典型形态。

### 去重

表格页的原始文本里已经有同样的行，只是被压平了。如果同时保留原始文本和结构化表格，同一份内容会在语料里出现两次。因此在表格通道产出后，**逐行比对**：表格已覆盖的行从文本块中删掉，其余行（例如表格周围的正文）保留；若整页文本都被表格覆盖，则文本块整体删除。

> 早先的版本用「表格字符数占该页 50% 以上就丢掉整块文本」，在一份 46 页的 PPT 导出件上把同页正文一起丢了。逐行比对不会。

### 幻灯片（PPT 导出）的两个坑

一份 46 页的 PPT 导出件把检测规则的假设全部打穿了：

1. **彩色区块被当成表格**。`find_tables()` 用线条策略，幻灯片里每个色块都是一个矩形，于是 **46 页全部**被判为表格页，每页 1–6 个"表格"。判别方法不是看形状（色块矩阵就是一个 2×2 表格），而是看**单元格内容长度**：真表格的单元格中位数 ≤ 60 字，版式块的中位数 ≥ 167 字。加上「至少 3 行或 3 列」和「表框不覆盖整页 85% 以上面积」两条，46 页降到 7 页。

2. **表格是图片**。有一页的表格整页是位图，文本层里只有标题和页脚（176 字）。它既不满足"无文本层"（有 176 字），覆盖率又只有 22%，旧规则一条都不命中，于是表格内容在整个语料里彻底消失。现在 `scan_like` 改成看**文本量与图片面积的对比**：字符数 < 400 且图片覆盖 ≥ 15% 即判为「内容不在文本层」，路由到 OCR。实测该页由视觉模型完整还原成两张 Markdown 表，行与列的对应关系正确。

## 切分策略与自动推荐

### 四种策略

| 策略           | 切分依据              | 适用            | 代价            |
| ------------ | ----------------- | ------------- | ------------- |
| `hybrid` 混合  | 先按标题/条款边界，超长条款内部再按语义断点 | 条款、制度、合同（推荐）  | 需 Embedding 调用 |
| `structured` 结构化 | 只按标题/条款边界，超长部分按段落/句子 | 有编号但不希望调模型    | 纯本地，毫秒        |
| `semantic` 语义  | 句子向量相邻距离的分位数断点     | 无编号结构的连续叙述    | 需 Embedding 调用 |
| `recursive` 递归 | 字符递归分隔符 + 重叠        | 基线对照，不推荐单独使用   | 纯本地，毫秒        |

### 为什么结构化优先

合同的含义活在编号里：章 / 节 / 条 / 一、/（一）/ 2.1 /（1）。按字符数硬切会把「第三条 付款方式」切成两个半句，两个半句都不能作为证据使用——引用会指错条款，模型也读不出完整义务。

解析器把两套并存的编号体系都覆盖了：

- **制度/法规体**：第X条 > 一、> （一）> 1.
- **合同体**：第X条 > 2.1 > （一）> （1）

小数编号按点号层数自动分层（`2.1` 为第 5 层，`2.1.3` 为第 6 层），因此 `2.1.3` 会嵌在 `2.1` 之下而不是把它顶掉。解析是纯正则，每页约 1 毫秒。

早期实现有一个必须记录的教训：最初每遇到一个叶子节点就产出一个块，一份 950 字的合同被切成 **17 块、平均 43 字**。条款完整率是 100%，但每块只装得下一条短款，检索质量反而低于不切。现在的产出规则是：

1. **单条永不截断**——`第三条` 只有 40 字就让它保持 40 字。
2. **连续同级节点向上累加到块长上限**，一块通常装 2–4 条完整条款。
3. **顶层祖先变化时强制落块**，因此一块不会横跨「第二章」和「第三章」，引用不会指错章。
4. 末尾过短的尾块，只有在与上一块同属一个顶层节点且放得下时才回并。

同一份合同修复后是 7 块、平均 107 字，条款完整率仍为 100%。

### 表格在切分里的处理

表格块不参与文本累加：它保持 `kind="table"`，按行切分，并且**每一片都重复表头**。没有表头的表格片段无法被理解，重复表头是让长表可读的唯一办法。图注块整块保留，不与正文拼接。

### 自动推荐

推荐器只读已抽取的文本，不调用任何模型，通常 1 毫秒内返回，包含策略、块长、重叠和**可读的理由**：

```
检测到 6 级标题、8 条条款，属条款型文档
结构优先切分：条款不跨块，检索命中即完整证据
超长条款再按语义断点切分，兼顾长度上限
结构切分不需要重叠：边界本身就是语义边界，重叠只会引入噪声
```

判定用的结构信号：

| 信号                | 含义                                |
| ----------------- | --------------------------------- |
| `heading_ratio`   | 命中标题正则的行占比                        |
| `max_depth`       | 编号最大层级                            |
| `article_count`   | `第X条` 数量                         |
| `styles`          | 编号风格分布（章/条/一、/（一）/1.1/…）         |
| `modality_density` | 应当/不得/可以/有权 等规范性用语的句子占比          |
| `p90_paragraph_len` | 段落长度 90 分位，用于决定块长                |
| `table_page_ratio` | 表格页占比，表格多时上调块长以免切碎表              |

规则本身只有四条分支，写在 `rag/chunk/profile.py` 里，没有隐藏的模型或阈值表：

- 有 `第X条` 或（标题占比 ≥ 1.5% 且层级 ≥ 2）→ `hybrid`
- 只有标题、编号稀疏 → `structured`
- 无编号且文本 ≥ 3000 字 → `semantic`
- 其余 → `recursive`

块长在 300–900 之间浮动：条款段落短（90 分位 < 320 字）时下调到 400，表格页占比 ≥ 20% 时上调到至少 700。`hybrid` / `structured` 的重叠固定为 0——边界本身就是语义边界，加重叠只会把上一块的尾巴带进下一块。

### 结构指标：能衡量什么，不能衡量什么

界面的四策略对比表用四个**零成本结构代理指标**，全部在本地计算：

| 指标     | 定义                        | 关注点          |
| ------ | ------------------------- | ------------ |
| 条款完整率  | `第X条` 标签完整落在单个块内的比例       | 有没有把一条切成两半   |
| 断句越界率  | 块末不是句末标点的比例（仅统计正文块）       | 有没有切在半句中间    |
| 长度命中率  | 块长落在目标窗口内的比例              | 有没有过碎或过大的块   |
| 类型保留率  | 表格/图形块仍以独立块存在的比例          | 表格有没有被压成普通文字 |
| 章节覆盖率  | 带章节路径的块占比                 | 引用时能不能说出出处   |

**类型保留率**是唯一能区分「保住表格」与「把表格碾平」的指标。语义切分和递归切分只在字符上做文章，一张表会被摊平成普通文本，表头也不复存在——前四个指标完全看不出来。

**两项指标会判定为不适用**，并从得分中剔除、按剩余权重重新归一：

- 文档里没有 `第X条` 编号 → 条款完整率不适用。否则「0 个条款的 100%」会被误读成满分。
- 句末标点行占比 < 20%（幻灯片、项目符号清单）→ 断句越界率不适用。那是文档本身没有句子，不是切分有问题。

结构得分 = 条款完整率 0.45 + (1−越界率) 0.25 + 类型保留率 0.30 + 长度命中 0.20 + 章节覆盖 0.10，仅对适用项求和后归一，再减去少量重叠冗余惩罚。

**这些不是检索精度。** 块数越少，指标越容易同时满足——把整篇塞进两块，条款完整率和越界率都完美，但那显然不是好切分。所以对比表必须同时看**平均字数**与**每千字块数**。真正的 `hit@5` / `MRR` 需要标注问题集，在 V6 引入；本版给出的只是「切分有没有尊重文档结构」这一层证据。

## 已知限制

- 无检索能力，问答依赖人工选页，受 `MAX_CONTEXT_CHARS` 限制
- 结构指标是代理指标，不是检索精度；真正的 `hit@5` / `MRR` 在 V6 引入
- OCR 与图注按页计费，默认关闭；单页 5–20 秒（模型差异很大），长文档需靠 `OCR_MAX_PAGES` 与 `OCR_MIN_INTERVAL` 控成本与频率
- 整页扫描件若无文字层且 OCR 也读不出内容，只能得到图注，得不到可引用的原文
- 多栏排版可能出现阅读顺序错乱，`detect_vertical=True` 只能部分缓解
- 表格块在页内按「正文 → 表格 → 图注」的顺序排列，不还原原始纵坐标位置
- 合并单元格的表格（跨列表头）会被拆出一个空列，pdfplumber 只能还原网格，还原不了合并语义
- 结构指标在无编号、无句末标点的文档（幻灯片、清单）上大部分不适用，此时只剩长度与类型保留两项有区分度
- OCR 输出的表格保留为 `ocr` 块，不进一步拆成结构化表格块
- 单文档、单进程、内存态，重启后需重新解析
- 无鉴权；开启 ngrok 即等于公开你的 API Key，用完请关掉
